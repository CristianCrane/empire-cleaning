# Web app

The one React app for the Office, Clients and Cleaners (ADR-0003), built with Vite. It talks to the server only through its JSON API. `pnpm dev` at the repo root starts it on http://localhost:5173.

Every screen is built from the design system in `packages/ui` (`@empire-cleaning/ui`). Its README covers the components, the Storybook catalogue and the browser setup the tests need.

## Areas and sign-in

Every route, the screen it draws and what it's for are in `docs/screens.md`.

- Someone signed out who opens an area goes to `/sign-in?next=…` and comes back to that page afterwards.
- An Account opening another role's area is sent to its own area.
- Staff with both roles start in the Office and switch areas from Switch to, among the account's parts (the sidebar's foot, the rail's Account or the ☰ menu's foot).
- Show tips again, among the account's parts, brings back first-time help's tours: every screen's shows once more.
- When a sign-in link has expired or been used, or a Google account has no Empire Cleaning Account, the person lands back on `/sign-in` with `?error=` and a plain explanation.

**Language** (ADR-0025): the screens' language is one store, `src/language.ts`, which each route sets as it decides it (`router.tsx`: an area's `areaLanguage`, the signed-out language before sign-in) and nothing else. The API is told it on every request (`api.ts`, `session.ts`), Root gives it to the design system's `LanguageProvider`, and `<html lang>` says it. Screens read their words through `useSaid(words)` (`src/screens/words.ts`, `docs/ux.md`, Language).

`src/session.ts` holds the Better Auth browser client (functions only, no UI), the areas and the signed-in Account with the first-time help tours it has seen (`seenTours`), asked of `GET /api/me` once and remembered until sign-out. The route guards live in `src/router.tsx`.

The signed-in Account is remembered, not asked for on every click. The app asks `GET /api/me` again when the person comes back to the tab (`src/main.tsx`), does something that can connect their Account to a record, or presses Show tips again. That is when it can have changed behind the app's back: asking for a Quote on the landing page, the Office adding a record, signing out in another tab. A tour seen is added to the remembered Account in place as well as sent to the API (`seeTour`), so it doesn't come back before the next look. Switch to, among the account's parts, shows the item pending until the area is ready, the ☰ menu or the rail's Account staying open meanwhile (#318, #305).

The Office's Dashboard also asks again every minute while it can be seen (`src/screens/office/Dashboard.tsx`), so a new Quote request shows on a screen left open. The Office is emailed of each one too. Live updates (websockets) weren't worth it: a request is promised a Quote within a working day.

In dev, Vite forwards `/api` to the server (`API_URL`, by default http://localhost:3000), so the app and the API share an origin and sign-in cookies just work. Production should do the same: serve the app and route `/api` to the server on one domain.

## First-time help

First-time help's tours (not the test site's tours of its demo people, `/people`) show a screen's parts once, the first time it matters (`docs/ux.md`, First-time help). Each area's tours are plain data in one file, `src/screens/portal/tours.ts` for the Client portal, `src/screens/office/tours.ts` for the Office and `src/screens/cleaner/tours.ts` for the Cleaner area, listed in `src/screens/tours.ts` (every area has its own, or the typecheck fails): an id the Account remembers it by, the route it's for, and one to three steps, each pointing at what's pressed (a link or Button, on the screen before the navigation) by its text, or at a part (a Section, a labelled group) by its name. `useTours` (`src/screens/run-tours.ts`, run by AreaLayout) starts one each time the router has drawn a screen (so after Show tips again, a screen's tour shows on its next visit): the first for that route the Account hasn't seen whose every step is on the screen and can be pressed (a greyed target, such as Mark done while the crew hasn't all confirmed or a Draft's Send before it can go, holds its tour back), through the design system's `startTour`. The first of an area's tours a person meets leads with its value line. Closing it, done or partway, marks it seen.

To add a tour, add it to its area's file and walk to it in `e2e/tours.spec.ts`. The walk through an area fails unless each of its tours ends up seen, so one whose step can't be found fails, and the spec fails while an area has no walk. Each walk goes through a tour from its data (`walkTour`), so a step's title and target are written once, in the tour. The spec runs with `test.use({ showTours: true })`; every other spec is spared the tours by the harness, which answers `/api/me` with every tour seen, in each browser a test opens (in the tours spec, each but the test's own page).

## Knowing where you are

Pages more than one step from their area's navigation start with `Breadcrumbs`, e.g. Clients › Casey Client (each screen's trail is in `docs/screens.md`). The navigation marks the section a page belongs to as current (`alsoCurrentFor` in `src/screens/AreaLayout.tsx`), so a Bill reached from a Client keeps Clients highlighted; a Cleaner's Job is under the section its crumbs start at (`jobSection`): Offers while it's offered to them, Your jobs once it's theirs.

## Links

Routing is TanStack Router, and design-system links (`Link`, AppLayout's nav) navigate through it. Every route is a named constant in `src/router.tsx`: written inline inside `addChildren()`, a route loses its types and so does every link. Screens read their data with `useLoaderData` from their route's `loader`, through `getJson` in `src/api.ts`. Every internal link loads its page ahead when the pointer rests on it, it takes focus or it's pressed down (`src/preload.ts`), so a route's `beforeLoad` or `loader` with a side effect skips it when `preload` is true, or the route sets `preload: false`. Every link is made with `linkTo()` from `src/links.ts`, which gives it the same checking as TanStack's own links: the route must exist, and its params must be given.

```tsx
<Link href={linkTo({ to: "/portal" })}>Home</Link>
```

A plain string or a hand-written `{ to }` object doesn't compile.

## Monitoring

Errors and about 20% of page loads go to Sentry (ADR-0007), set up in one place: `packages/browser-monitoring`, started in `src/main.tsx` and built in by `vite.config.ts`. Its README lists what may be sent and what mustn't.

- **Set at build time:** `VITE_SENTRY_DSN` (without it nothing is sent, as in dev and the tests), `VITE_APP_MODE` (the environment: `test` on the test site) and `VITE_LANDING_URL` (the landing site, whose Privacy policy and Terms of service sign-in links: `http://localhost:4321` unless set, the same address as the server's `LANDING_ORIGIN_URL`). With `SENTRY_AUTH_TOKEN` and `SENTRY_ORG`, source maps are uploaded to Sentry's `web` project and never published. Every build marks its code as ours, token or not (`monitoringBuild`, `packages/browser-monitoring`). The release is the git commit, the same as the server's.
- **Feedback, on the test site only:** a floating Send feedback button on every page (`feedbackButton(feedbackLook)` in `src/main.tsx`, only when `VITE_APP_MODE` is `test`, so other builds leave its code and look out), so the owner can report what they find with a comment and a screenshot. `src/feedback.css` keeps it above the phone's tab bar and any `ActionFooter`; its look, under every Dialog in the app's colours and theme, is the design system's (`@empire-cleaning/ui/feedback.css`), shared with the landing site. `src/feedback.test.tsx` checks each.
- **Reported:** errors nothing caught, and every one a screen catches but didn't expect, through `reportUnexpected` (`src/monitoring.ts`); the lint rule `empire/report-unexpected` (`packages/lint`) holds every catch to it. Never the API's answers: a 5xx is reported by the server, and a 4xx is normal business. Nor a dropped connection, nor a card the Client couldn't use. Stripe's other errors (a wrong key, a bad request, Stripe failing) are ours, and reported (`cardProblem` in `src/screens/portal/CardForm.tsx`).
- **Traced:** page loads and page changes, named after their routes and linked to the API's traces of the calls they made.
- **Who:** the signed-in Account's ID (`identify` in `src/session.ts`), never their name or email.
- **Never sent:** session replay, form values, request bodies, cookies, console lines, or emails, phone numbers and query values anywhere in an event.

## Testing

End to end with Playwright (`e2e/`): a production build of the app runs in a real Chromium against the real API and a real database, on the test Postgres.

**Tests run in parallel, and each worker has a slot of its own** (`e2e/slots.ts`): an API with its control server and database (`empire_e2e_test_r<run>_0`, `_1`, …, named for the run as in the server README), and the built app served in front of it. A test only ever sees its own slot's data, emails and clock, so any test can run beside any other. There are 2 workers (why: ADR-0032); `E2E_WORKERS=6` or `--workers=6` sets it, and only that many slots start, so run one spec with `--workers=1`. Every slot's ports come from the block of ports leased for the run (`E2E_PORTS`, see the server README), and the run builds the app into `dist/e2e-<first port of the block>` and keeps its traces in `test-results/<first port>`, so other runs, in this checkout or another, can go on at the same time. A block's folders are reused by the next run on it. A test reaches its API through `apiUrl` from `playwright.config.ts`, never a fixed port. CI splits the suite across several jobs (`--shard`, `.github/workflows/ci.yml`).

**The phone is the main screen and runs everything; the desktop runs only the tests tagged `@desktop`**, those where a larger layout changes something (the sidebar, two-column prices, light-theme accessibility). Tests tagged `@smoke` are the quick set (`pnpm test:quick`). Tag a test with `test("…", { tag: "@desktop" }, …)`.

`e2e/layout.spec.ts` opens every screen at widths from 320px to 1440px and fails if an input is narrower than its text, the page scrolls sideways, a button or link sits under a fixed bar such as the phone's tab bar (where the screen opens for one in a fixed or sticky box, scrolled to the middle for the rest; #425), or its text has a doubled stop ("a.m..", `docs/ux.md`, Language); a Guest's or Client's screen in Spanish too (`expectFitsInBoth`: the Client's Preferred Language through `setLanguage`, or `?lang=es` before sign-in), as Spanish runs longer (ADR-0025). The other tests read values from the DOM, which is there whether or not anyone can see it, so they can't notice text squeezed out of sight. Add new screens to it. `e2e/spanish.spec.ts` runs sign-in and the portal's core flows once each in Spanish.

A test starts signed in with `signedInAs(page, email)`, which signs the person in for real through the control server and hands the browser the session; only the sign-in tests use the form, the email and the link (`signInWithLink`). Only email, payments and the clock are faked, with the same fakes the server tests use (`packages/server/tests/e2e/server.ts`). Every browser a test uses keeps to the API's clock (`browsers` and `control` in `e2e/harness.ts`, #520): it starts where the clean slate leaves it, 9:00 UTC on Monday 5 January 2026, runs on from there, and moves wherever a control call moves the API's, so a page shows the same day and time the API stamps its records with. A test moves time with `setClock`, never the browser's clock alone; `page.clock.runFor` and `pauseAt` only run a page's timers on by hand. The payment forms are Stripe's Payment Element (`src/screens/portal/CardForm.tsx`, cards only, themed from the tokens), with the consent to later Charges beside them. The fake payment provider asks for its own "test" form instead, which needs no card typed; `failCharges()` makes Deposits fail and `requireApproval()` makes the Client's bank ask for approval, which the test form gives at once.

**What the fake covers, and what the sandbox run does.** The fake payment provider covers every screen's handling of a payment's outcome: paid, declined, approval asked, given or refused, a bank debit clearing. It never loads Stripe's form, so nothing here types a card, confirms with Stripe.js or meets 3D Secure. `e2e/card-form.sandbox.ts` does, against a Stripe sandbox: the same built app, under its CSP, and the same API with the real Stripe adapter in place of the fake (`packages/server/tests/harness.ts`), typing Stripe's test cards into the Payment Element. Its cases: accepting a Quote with a card (the Deposit taken and the card saved), with 3D Secure approved and failed, with a declined card; saving a card as the Payment Method; paying a Bill on its page. It runs nightly after the contract run (`.github/workflows/stripe-sandbox.yml`); run it by hand when `CardForm.tsx`, Stripe.js or the CSP changes, with Postgres up and a sandbox's keys in `packages/server/.env` (or `STRIPE_SANDBOX_SECRET_KEY` and `STRIPE_SANDBOX_PUBLISHABLE_KEY`): `pnpm --filter @empire-cleaning/web stripe:sandbox`. It's outside `pnpm test` and `pnpm test:change`, which take only `*.spec.ts`, so it finds each form it pays through with the harness helper the PR's specs use (`docs/testing.md`, Rules, which names what stays its alone).

Check accessibility with `expectAccessible(page)` from `e2e/harness.ts`, and switch area with `switchArea(page, area)`: `docs/testing.md` has both rules and the bugs behind them.

```sh
pnpm --filter @empire-cleaning/web test       # needs Postgres (pnpm db:up) and Chromium
pnpm --filter @empire-cleaning/web test:e2e   # just the end-to-end tests
```

While working on a change, run only what it touches (the root `README.md` says what runs before the PR):

```sh
pnpm test:change e2e/bills.spec.ts                                         # the specs the branch adds or edits and the specs named, once each, and the other packages' tests
pnpm --filter @empire-cleaning/web exec playwright test e2e/bills.spec.ts  # one spec
pnpm --filter @empire-cleaning/server exec vitest run --changed main      # server tests affected by changes since main
pnpm test                                                                  # the @smoke set and quick suites of every package
```

`pnpm test:change` finds the specs the branch adds or edits from git, but a change in `src/` is in no spec: name the specs for the screens you changed. A change to what a route's URL takes (a Tab, a search word, a path) reaches every spec that opens that URL, whatever screen it tests: search the specs for the old value (`rg 'tab=all' packages/web/e2e`) and name each one, as #433 retiring Clients' All Tab broke three tests in the Bills and asking specs, which no List spec covered. It doesn't use Playwright's `--only-changed`, which takes every spec importing a changed file too, so an edit to `e2e/harness.ts` would run nearly all of them.

**Screenshots for a PR.** A PR that changes a screen shows it before and after in its body. `pnpm pr:shots packages/web/e2e/people.spec.ts "<test title>"` (add `--desktop` when the larger layout differs, `--viewport` for the screen alone) runs one test twice, a landing site spec too (`packages/landing/tests/…`), and takes a full-page screenshot at its end: before on the branch's merge base with origin/main, in a worktree beside this checkout (`<checkout>-shots-base-<first port of the run's block>`, gone when the run ends, so two runs in one checkout keep apart; one a killed run left is removed by the next run once no run holds that block), and after in this checkout. Each side runs with its own checkout's Playwright, harness, slots and databases (`packages/server/tests/e2e/shots.config.ts` wraps the package's config), so the before is shot as the base's `prShot` shoots: on a branch older than a change to it, merge main in first. Both sides use the one block of ports the run leases (`packages/server/tests/ports.ts`), as they run one after the other. The PNGs go to the orphan `pr-media` branch, in a folder named after the branch, so the public PR shows them inline, and it prints the table to paste under **Before / after:**; a copy of each stays in the checkout's git dir, under `pr-shots/<first port of the run's block>/`, until the next run. The shot is the screen at rest, as a person would see it: each package's harness (`prShot`, in `e2e/harness.ts` and the landing site's `tests/harness.ts`, both calling `packages/server/tests/e2e/at-rest.ts`) lets go of focus and hover and hides the toasts first, so a test needs no lines of its own for the picture. Each project draws at a power of two pixels a point, the one at or below its own, the landing site's too: the phone at 2, not the Pixel 7's 2.625, so its shots are 824 px wide, and desktop at 1. At 2.625 an icon's edge came out one of two ways, a few pixels apart, from run to run (#488). It makes the screen as tall as the page before the shot, so what's pinned to the screen sits where a person sees it as they scroll: the top bar at the page's top, the tab bar and an `ActionFooter` at its foot (Chromium's own full-page shot draws them wherever the screen was, mid-page, #414). What's sized by the screen's height runs the page's height too, such as the desktop sidebar, with the account at the page's foot. A test the base doesn't have runs there from the branch's copy of the spec's test folder (`e2e/` or `tests/`, so a helper it imports comes too), on the base's own app and server, and the output says so; one that fails or won't load there gives an after alone (#402). A project a test skips (`test.skip(isMobile, …)`) gives no shot there, and says so; a test that fails on either side, or a title that names no test or several, pushes nothing, and says which side. Pick a test that ends on the changed screen as a person opens it: no open menu (an a11y test that ends on another person's page, or one that just pressed a Button, won't do). When none ends that way, add one, as PR #409 did. A full-page shot lays the page out at its full height, so it can't show what a fixed bar covers at rest (the tab bar over the Quote Draft's Send, #425): add `--viewport` for the screen as the test left it, scrolled where it ended, with the bars over what they cover (#430). A change that should leave every screen as it was (a refactor moving screens onto a layout) shows that with `pnpm pr:shots --same <spec>…` (with `--desktop` too, and `--viewport`): it runs every test in the specs on each side, takes each one's end fresh, compares the before and after byte for byte, and prints "N of N identical" for the PR, listing the tests that differ and any on one side alone. One commit doesn't always shoot a test the same twice: the landing site's Quote requests send a random email (docs/testing-log.md, 2026-11-20), while two runs of the web app's suite shoot every test that opens a page the same (#488), bar one short shot seen once, cause not shown (#491). So the base runs twice, and a test whose two shots there differ is listed as not compared: check those by eye. A test listed as different has its pair published: look at it. A landing spec compared against a base older than its harness's `prShot` reads Different on every test, as the base's shot is Playwright's own, taken as the page may still be loading: merge main in first. It takes three runs of the specs. It publishes only the pairs that differ, plus the first identical one on each project, with the table for each. A test the base lacks runs there from the branch's tests, as above; one test failing on either side stops it, pushing nothing (#439, #438). A prototype (`docs/ux.md`, Changing a screen) is shot with `pnpm pr:shots --prototype <screen>`: the web app's or the landing site's, found by its file, every layout × case at rest at the widths `WIDTHS` names in `packages/server/tests/e2e/prototype-shots.ts` (a phone's on the phone project, the rest on desktop), run through each package's `prototype.shots.ts`, which no other run takes. It shoots this checkout alone and publishes nothing, as a prototype has no before and no PR: the shots and an `index.md` showing them, a heading a case and a row of widths a layout, stay in `pr-shots/<first port of the run's block>/`, and it prints that path.

Small screen-only behaviour can still use Vitest browser tests (`src/**/*.test.tsx`), as the design system does.
